# Lessons Learned — Apuntes de Guitarra

> Doctrina derivada de las auditorías y pasadas de resolución del proyecto. Captura los **patrones de error** que produjeron las violaciones encontradas, para no repetirlos. DESIGN.md codifica las reglas; este documento explica los modos en que las reglas se pierden y cómo cazarlos antes de que entren al codebase.

## Cómo nació esta deuda

El frontend fue migrado por partes desde un repo personal (`apuntes-guitarra`) que nunca pasó por una auditoría de diseño. PRODUCT.md y DESIGN.md se escribieron **después** del código, lo que significa que muchos patrones del repo original quedaron como hechos consumados — algunos compatibles con la doctrina ("Cuaderno de Estudio del Profesor"), otros directamente reflejos del dataset (SaaS-cream, Notion-callout, rainbow tags). Esta tensión es la fuente de las violaciones.

## Patrones de error documentados

### Migración drift

Estos son los modos concretos en que el código original se desvió de la doctrina, observados durante las auditorías. Si encontrás cualquiera de estos en código nuevo, paralo antes de hacer commit.

- **Arrays decorativos de "colores bonitos" indexados por algo no-nota.** `ROLE_COLORS = ['#c0392b', '#27ae60', '#d4a017', '#2980b9', '#8e44ad', '#1abc9c', '#e67e22']` en `data/triads.ts` y `STATE_COLORS = { tonica, highlighted, neutral, natural, userPicked: '#2980b9' }` en `ChromaticCircleAnimated` son la misma especie. Nacen del impulso "necesito N variantes visuales, acá hay N colores saturados" sin preguntarse si la variable que se discrimina (rol intervalico, estado de selección, categoría) **es** una nota. Regla de detección: si escribís un array de colores y el index name no es un nombre de nota o de acorde, es olor.
- **`var(--stringN)` se siente como design system, pero es una nota disfrazada.** Cada cuerda al aire ES una nota (E A D G B E). Cada forma CAGED ES una raíz. Importar `var(--string6)` para colorear un intervalo en `IntervalsSection` viola la cuarentena tan literalmente como escribir `#8e44ad`. Auditar: cualquier consumidor de `--stringN` o `--caged-*` que **no** sea una visualización de cuerda/CAGED es violación.
- **`#fff` puro casi nunca es la excepción del Signature Component.** La excepción es estrecha: glifo de letra blanco dentro de un círculo de nota saturado. Bordes decorativos, anillos de "selección", indicadores de "raíz", separadores y stroke de hover NO califican — usan `var(--paper)`. Test: ¿el `#fff` está en un `<text>` SVG inmediatamente sobre un `fill={NOTE_COLORS[X]}`? Sí → exento. No → reemplazar. **Cuando el código sí cae en la excepción legítima, dejar comentario inline** (`/* Signature: letra blanca sobre nota saturada, no tokenizar */`) para que un agente futuro no "corrija" el patrón.
- **Hex literals que se repiten ≥3 veces son tokens faltantes.** Cinco instancias de `#b8b0a5` en `*.module.css` con la misma semántica (texto de cuerpo) y mismo `font-size`/`line-height` son una señal: necesitás un token. Eso fue exactamente `--text-body`. Antes de añadir el sexto literal repetido, pará y creá la var. Patrón: `:root { color: X }` + `[data-theme="light"] { color: Y }` paralelos en cualquier archivo es una pista directa.
- **Hex hardcoded que funciona en oscuro silenciosamente rompe en claro.** El commit `fe723cd` cazó la mayoría, pero la 2ª ola limpió el residuo: `#b8b0a5` (6 archivos), `STATE_COLORS.neutral.fill = '#1a1a1a'`, mástil de intervalos completo, `LockScreen` error color `#e25555`. Test continuo: `grep -E "#[0-9a-fA-F]{3,8}"` en cualquier `.module.css` o `.tsx` debe revelar solo (a) tokens del front-matter de DESIGN.md, (b) hues de nota en `data/notes.ts`, o (c) el frame buffer Signature Component.
- **Playfair Display para "tono editorial".** El reflejo entrenado dice "italic serif = premium content vibe". DESIGN.md prohíbe Playfair en cualquier UI copy que no sea una cita literal de Josué. El subtítulo eliminado de T2 (*"Un recorrido por el método de Josué Barquero"*) y la pregunta de ProcessPanel (*"¿Cómo saber la armadura..."*) son ambos casos donde Playfair se coló como "ambiente". Si una fuente tiene una Named Rule fijando su único caso de uso, **cualquier otro uso es una falla del diseño**, no una interpretación creativa.
- **Headers de módulo replicando el header global.** El `<h1>Tonalidades y Armaduras` de `T2Module` heredaba el modelo mental "module landing page" de templates React genéricos. Estructura: centered title + tagline + 60-80px hero padding. Esa estructura es legible para el dataset como "section opening" y empuja todas las decisiones hacia el centered-hero default. Pregunta a hacerse antes de añadir cualquier shell de módulo: **¿esta superficie necesita un header, o estoy heredando uno porque todo producto tiene uno?** En esta app, la respuesta por defecto es no — AppShell + Header global poseen la identidad de página.
- **Em dashes (`—`) como separador "tasteful".** El reflejo del LLM es usar em dash en numbered list/section labels (`"01 — Title"` lee como editorial pattern del dataset). El estándar del proyecto es `·` (U+00B7), que el modelo "autocorrige" a em dash si no se le pinta explícitamente. Codificado en DESIGN.md §3 como Middle-Dot Separator Rule. **Auditorías de em-dash deben extender el scope a `.json`** (locales i18n) y `.md` además de `.tsx`/`.module.css` — es ahí donde se esconden.
- **`React.CSSProperties` inline en componentes nuevos.** `Footer.tsx`, `MasterTriad.tsx h2 style`, `ChromaticCircleAnimated STATE_COLORS`. Los estilos inline no son violación per se, pero (a) inhiben theme-flipping cuando hay hex literales, (b) escapan el linting de CSS modules, (c) hacen que las violaciones sean invisibles a buscadores tipo `grep "border-left"`. Default a CSS module; reservá inline para valores genuinamente dinámicos (computados en render).
- **Side-stripe borders (border-left: 3px) entrando como código nuevo, no solo legacy.** `RuleNote` está documentado como deuda legacy. Pero `ProcessPanel.stepActive`, `TablaMaestra.rowActive`, y `FExceptionBanner` los reintrodujeron en código del POC T2. Fueron resueltos en la 2ª ola (bg tint + font-weight + chevron, o full border 1px). Cualquier `border-left` o `border-right` >1px coloreado en componente NUEVO es violación inmediata. **Cuando elimines un side-stripe, revisá el `border-radius` y el `padding` adyacente** — ambos suelen ser artefactos del stripe (ej: `border-radius: 0 4px 4px 0` solo existe porque hay un side-stripe izquierdo). Layout shift hidden inside the stripe.
- **`rgba(0, 0, 0, X)` y `rgba(255, 255, 255, X)` sobreviven múltiples olas de auditoría.** El sidebar overlay `rgba(0,0,0,0.6)` y el watermark del Header `rgba(255,255,255,0.03)` pasaron las olas 1 y 2 sin ser tocados — solo cayeron en la 3ª. Sospechosos: rgba con valores 0,0,0 o 255,255,255 son menos visibles a grep que hex puros, y muchas auditorías de tema solo buscan `#000`/`#fff` literales. **Lint regex propuesto para CI:** `/rgba\(\s*(0\s*,\s*0\s*,\s*0|255\s*,\s*255\s*,\s*255)/` en `*.module.css`. Las excepciones sancionadas (sombra del fretboard dot, hover glow de Triads) opt-in vía comentario marker.
- **`React.CSSProperties` inline es el último refugio del estilo no-tokenizado.** El `Footer.tsx` sobrevivió 2 olas porque no aparece en greps de CSS modules ni de hex literals. Patrón: cualquier `style={{...}}` o `const x: React.CSSProperties = {...}` en componente nuevo bypasa simultáneamente la convención de CSS modules Y el sistema de tokens. **Audit grep:** `style={{|React\.CSSProperties` en `src/components/**/*.tsx`. Default a CSS module siempre; reservá inline solo para valores computados en render (no decisiones estilísticas).
- **CSS-var indirection a través de un mapa TypeScript es el patrón limpio para paletas theme-aware.** `NOTE_COLORS` pasó de hex literals a `'var(--note-c)'` strings en `data/notes.ts` sin tocar un solo consumidor — los 4 componentes que la consumen (`ChromaticNode`, `TriadNode`, `MasterTriad`, `TriadsSection`) usan los valores via SVG `fill`/`stroke` o inline `style.color/background/borderColor`, todos los cuales aceptan `var()` strings nativamente. Cuando un mapa de tokens previamente fijo necesita variantes por tema, esta es la migración mínima — antes de considerar refactorings mayores como theme context o derived state, intentá el truco del `var()` string.
- **Yellow-on-cream es la trampa universal de paleta.** El amarillo `#f1c40f` (luminance ≈ 0.59) es físicamente imposible de pasar AA sobre cream warm `#f5f0e8` sin colapsar a ochre/mostaza. Cualquier sistema con tema cream + slot semántico "yellow" debe aceptar un **cambio de familia de hue**, no solo un darkening. Documentar el trade-off explícitamente en lugar de "hacer como que sigue siendo amarillo".
- **Centralized side-effect kill switches escalan mejor que opt-outs por componente.** Tres `if (audioMuted) return` lines en `useAudioEngine` neutralizaron audio en 9+ archivos consumidores. La alternativa (pasar un flag a cada componente) habría sido un diff mayor y se reaplicaría para cada nuevo componente que dispare audio. Patrón: cuando un side-effect se dispara desde N lugares, el kill switch va en el dispatcher, no en los call-sites.
- **`store.getState()` dentro de callbacks memoizados es más seguro que suscribirse via hook.** Evita stale-closure bugs con `useCallback([], ...)` deps y evita re-crear callbacks en cada cambio de estado (que re-dispararía `useEffect` cleanups en consumidores). Suscribirse en el árbol React solo cuando necesitás re-renders; leer imperativamente cuando solo necesitás el valor actual al momento de la llamada.
- **Excepciones doctrinales pertenecen al documento de doctrina, no como overrides silenciosos.** Cuando una regla rígida ("note hues fijas a través de temas") choca con una restricción dura (WCAG AA), la respuesta correcta es documentar la excepción con su trade-off (la "Light-theme overrides" subsection en DESIGN.md §2), no romper la doctrina y mover los hues a otro archivo. **Test:** un agente futuro leyendo DESIGN.md debería entender por qué la doctrina parece contradictoria. Si solo ve los CSS vars sin contexto, asumirá que la doctrina está rota.
- **Cuando una doctrina marca "excepción legacy", el fix es mecánico: alinear con el patrón sibling canónico.** RuleNote era el último callout con side-stripe; FExceptionBanner ya había migrado al patrón "full border 1px + tinted bg 6%" en la 2ª ola. La 4ª ola simplemente replicó esa receta exacta — incluyendo el magic number `0.06` del tint. **Reusar valores entre callouts paralelos es más valioso que optimización per-component**.
- **Primitivas migradas con chrome interno (SectionLabel + `<h2>` + section wrapper) chocan con módulos que numeran sus propias secciones.** `ChromaticCircleSection`, `IntervalsSection`, `TriadsSection` venían del repo personal con SectionLabel hardcodeado ("03 · Notas", "05 · Intervalos", "06 · Acordes") y `<h2>` propio. Cuando T1Module las envolvió en sus secciones 02/03/06, hubo doble label + doble h2 + numeración cruzada. La fix correcta: la primitiva renderiza solo la visualización interactiva (SVG, mástil, NoteSelector), el consumer provee SectionLabel + h2 + prose. Patrón generalizable: **una primitiva no debería tomar decisiones de chrome editorial (numeración, jerarquía, separadores) que pertenecen al módulo que la consume**. Test: si la primitiva tiene `<SectionLabel>` o `<h2>` hardcoded, no es primitiva — es sección.
- **Discriminar roles dentro de un sistema con identidad de color fija exige cuatro dimensiones no-color.** En `EscalaMayor` los 4 roles (tónica, estable, tensa, off-scale) NO pueden discriminarse por color (cada nota ya tiene su hue fijo). El reflejo del LLM es introducir `STATE_COLORS = { stable: '#X', tense: '#Y' }` — exactamente la violación que la Note-Color Quarantine bloquea. La discriminación válida requiere combinar **opacity + tamaño + stroke + presencia de label** simultáneamente: opacity 1.0/1.0/0.55/0.2, radio 22/18/18/11, ring `var(--paper)` sólo en tónica, label visible sólo en notas de la escala. Una sola dimensión no alcanza (opacity sola es ambigua entre estable y tensa); cuatro juntas dejan claro el rol sin importar segundo color. **Patrón generalizable:** cuando un componente tiene identidad de color fija por elemento (notas, semáforos de status, severidades, etc.) y necesita superponer un eje de "rol", el rol vive en propiedades NO-color. Es preferible tres atributos no-color que un atributo color falso.
- **Spelling enarmónico estricto produce dobles accidentales en tónicas extremas.** `majorScaleSpelled('D#')` devuelve `[D♯, E♯, F♯♯, G♯, A♯, B♯, C♯♯]` — teoría musical correcta, lectura inusual. La práctica pedagógica resuelve esto eligiendo la enarmonía bemol (E♭ mayor en lugar de D♯ mayor). Decisión doctrinal: implementar la regla teórica fielmente, dejar el costo visual como deuda documentada, NO ocultar la corrección teórica con auto-redirección a flats. Test futuro: si emerge fricción real con estudiantes pidiendo "Eb", la solución correcta es añadir entrada flat-aware al selector (no romper el algoritmo). Aplicable a cualquier visualización musical que respete spelling: la teoría manda, el visual se adapta.
- **`<NoteToken>` no es violación de la cuarentena — es su uso canónico en prosa.** La Note-Color Quarantine prohíbe usar `--note-X` para decorar UI no-nota. Pero un span de texto que **es** el referente concreto de una nota individual (ej: la "F" en "La tríada de F es F A C") **es** una nota — y por ende califica para usar su hue. El test sigue siendo: ¿este elemento, individualmente, representa una sola nota? Sí → token válido. No → violación. Conceptos como "tónica", "intervalo", "tensa", "estable", "mayor", "menor" NO son notas; son roles, tipos o estados — usan neutros + acentos de marca. El error de auditoría futura típica será confundirlo: un agente al ver `<NoteToken>` puede pensar que "se relajó la cuarentena" y empezar a usar note hues para destacar conceptos. **La cuarentena NO se relajó — se hizo explícita la condición que siempre permitió.**
- **Prosa con notas: `ProseSegment` antes que regex en render time.** Tentación natural al ver "F → A → C." en un string es: parsear con regex en el componente y reemplazar cada match con `<NoteToken>`. Eso es brittle (qué pasa con "Fa" o "Bm"?) y empuja la lógica de tokenización al consumer. La solución correcta es estructurar el dato: `ProseSegment = ({type:'text'} | {type:'note'})[]`. El tokenizado se hace una vez en `literalContent.ts` por una persona que lee el contexto, no por un parser que adivina. **Patrón generalizable**: cuando un texto tiene partes que son referentes semánticos de elementos del sistema, estructurar el texto como árbol de fragmentos tipados, no como string a parsear.
- **Tipo permisivo (`NoteSpelling`) vs estricto (`ChromaticNote`) aparece cuando el método tiene fidelidad enarmónica.** `ChromaticNote` solo cubre sostenidos (12 valores). El método de Josué usa bemoles libremente (Bb, Eb, Db, Ab, Gb). Forzar el dato a sostenidos rompe fidelidad de fuente; widening a un superset permite preservar el spelling original. Pattern para futuras situaciones: cuando el dominio de los datos es más amplio que el dominio de las primitivas técnicas (audio engine resuelve enarmónicamente, pero el método los nombra distinto), el tipo de display ≠ el tipo de identidad técnica. Mantener ambos: identidad técnica para audio/visualización, spelling para texto.
- **Spellings inválidos se preservan como texto plano, no como token.** El método cita explícitamente `B#`, `E#`, `Fb` en contextos negativos ("se omiten", "no es"). Tokenizarlos requeriría inventar mapeos enarmónicos que el método no usa, perdiendo el contraste pedagógico. Decisión: NoteToken solo cubre los 17 spellings canónicos (12 sostenidos + 5 flats que el método usa positivamente). Lo demás queda como texto. **Test:** ¿este nombre aparece nombrado positivamente como una nota a tocar/escuchar? Sí → token. No (mencionado como contraejemplo o spelling rechazado) → texto.
- **Para ruido visual por densidad, el *número* de elementos pesa más que el *peso* de cada uno.** La 8ª ola probó bajar el bg tint del NoteToken de 12% → 8% (mitigación A) en respuesta a la deuda de densidad alta. Resultado: en frases cortas se sentía más calmo, pero en pasos con 14+ tokens consecutivos el "rainbow chip salad" persistía — porque el ruido viene de tener N chips simultáneos, no de cada chip por separado. Atenuar cada chip al 33% deja N chips al 67%, sigue siendo N chips. La fix correcta fue **eliminar la capa de chips** (mitigación B): sin background, la identidad la sigue cargando el color del glifo (canónico), y la densidad se vuelve "secuencia de letras coloreadas" en lugar de "pila de chips". Patrón generalizable: cuando una decoración por-elemento se acumula visualmente bajo densidad alta, cuestionar si la decoración debe **existir** antes que cuánto debe **pesar**. Lower opacity is not always the answer; sometimes the layer should not be there.
- **Sustracción cierra deudas que tuning no cierra.** La deuda de densidad estaba documentada con tres mitigaciones (A bajar, B quitar, C atenuar). Las tres son váhlidas, pero solo B es **estructural** — A y C son tuning del mismo paradigma (chip-with-tint). Cuando una deuda se documenta con un menú de mitigaciones, vale la pena identificar cuál es estructural y cuáles son grados del mismo eje, y considerar la estructural primero si el contenido lo permite. La estructural suele cerrar la deuda; las de tuning suelen postergarla.
- **Cuando se discrimina por una dimensión no-obvia, una leyenda explícita evita que el encoding pase desapercibido.** En `TensionResolucion` las flechas codifican jerarquía de tensión en `stroke-width` (1.5 / 2 / 2.5 / 3) — discriminador legítimo bajo la cuarentena de color, pero no auto-evidente en lectura rápida (un usuario podría pensar que "más grueso = más enfático" sin entender la regla pedagógica del 1 s.t. vs 2 s.t.). La leyenda en Plex Mono + swatches con `border-top-width` matching aclara el encoding sin caer en tooltips ni overlays. Patrón generalizable: **discriminadores no-color (peso, tamaño, opacity, posición) suelen necesitar una leyenda inline** cuando la decisión de discriminación está cargada de significado pedagógico/semántico. Color es auto-explicativo (rojo = peligro, verde = OK como instinto cultural); peso/tamaño no lo son.
- **Debounce compartido por shared ref para multi-trigger interactivo.** SVG `<path>` interactivo con `onClick + onFocus + onKeyDown` simultáneos sufre el problema clásico: mouse click dispara click + focus en sucesión, audio se reproduce dos veces overlap. Solución: `useRef<number>(0)` para `lastFireTime`, todos los handlers chequean `now - lastFireRef.current < 150ms` y descartan. Pasa el tabbing genuino (siempre >150ms entre tabs reales) y bloquea el doble-trigger del click. Más simple que `setPlaying` boolean por elemento, más robusto que `e.stopPropagation()`. Patrón generalizable a cualquier elemento con tres triggers que pueden disparar el mismo efecto.
- **Tabla pedagógica que se transforma > N tablas apiladas.** Cuando la enseñanza es "la misma tabla revela más verdad a medida que el estudiante avanza" (procedimiento de 3 pasos, derivación incremental), la tentación es renderizar N tablas (una por estado). Resultado: pierde la pedagogía de la *transformación*, el ojo del estudiante salta entre tablas en lugar de ver cómo crece la misma estructura. Mejor: una sola tabla con filas adicionales pre-renderizadas con `opacity: 0`, reveladas con transición de opacity al estado correspondiente. El espacio vertical se reserva desde el estado 1 (la tabla "se siente completa estructuralmente") y la pedagogía vive en la transformación visible. Pre-render evita animar layout properties (cumple Don't 10) y el costo es estético menor (los slots vacíos en estados tempranos se leen como "más viene"). Aplicado en §4.7 Grados armónicos (10ª ola).
- **Tipografía como discriminador completa el set de "no-color discriminators".** La 6ª ola usó opacity/size/ring para 4 roles. La 9ª ola usó stroke-width para 4 niveles de tensión. La 10ª ola usa **tipografía** (peso + caso + tamaño + estilo) para 3 calidades de acorde: I/IV/V Plex Mono bold uppercase 16px (mayor), ii/iii/vi Plex Mono regular lowercase 14px (menor), vii° Plex Mono italic 12px (disminuido). Discriminación robusta sin tocar la paleta. **Patrón generalizable**: bajo Note-Color Quarantine, los tres ejes no-color disponibles son (a) opacity/size/ring (geométrico), (b) stroke-width/font-weight (peso), (c) caso + estilo + tamaño (tipográfico). Cualquier discriminación de N elementos no-nota debe combinar estos antes de tocar la paleta. Si un eje no alcanza, combinar dos; si dos no alcanzan, considerar si el componente está intentando codificar demasiada información a la vez.
- **`[data-diatonic]` debe declararse DESPUÉS de `[data-note]` en el mismo módulo CSS.** Ambas reglas usan el mismo nivel de especificidad (`.token[data-attr="val"]`). Si `[data-diatonic]` aparece antes de `[data-note]`, los colores cromáticos ganan y el override diatónico queda silenciado — el componente se ve correcto en test básico (note sin diatonicRole) y roto en el caso de uso principal (note con diatonicRole). Detección: si el prop `diatonicRole` existe en el DOM pero el color sigue siendo el del hue cromático, el orden de declaración está invertido. Aplica a cualquier sistema que superponga un eje de rol sobre identidad fija vía `[data-*]`.
- **Hover ≠ select en elementos de nota interactivos.** El reflejo del LLM al añadir interactividad a una nota es: `onMouseEnter` → cambiar estado global. Pero hover es feedback (el usuario está explorando) y click es decisión (el usuario eligió). Conectar `setTonic` a `onMouseEnter` produce cambios de tónica accidentales mientras el cursor cruza la tabla. La regla: `onMouseEnter`/`onFocus` disparan SOLO side-effects reversibles (audio que para solo, highlight temporal); `onClick` y `onKeyDown(Enter|Space)` disparan cambios de estado persistentes (tónica, selección, modo). Test: pasar el cursor lentamente sobre 7 NoteTokens — si la tónica global cambia, el binding es incorrecto.
- **`toAscending()` para secuencias de notas sin octava explícita.** `chordSpelled` retorna `ChordMember[]` con octava precalculada. Pero cuando el array de entrada es `NaturalNote[]` (TRIADS data, sin octava), tocar todos a oct. 4 produce inversiones de voz: F-A-C en oct. 4 baja C4 por debajo de F4. El helper correcto itera la secuencia, compara `NATURAL_SEMITONES[n]` con el semitono anterior, e incrementa octava cuando `semi ≤ prevSemi`. Patrón generalizable a cualquier ordenamiento melódico de notas sin `ChordMember` structure: derivar octava incrementalmente desde la secuencia, no asumir octava fija.
- **Em dashes en mi propio draft dentro de `literalContent.ts` NO son automáticamente "citas literales".** La regla codificada dice "em dashes ok en `literalContent.ts` para citas literales del método". El agente que escribe párrafos pedagógicos parafraseando el source puede convencerse de que "esto es contenido, los em dashes están permitidos acá". No lo están — sólo el texto verbatim del método (ej: `EXCEPCION_F_COMPLETA` que cita un párrafo entero entre comillas) gana la excepción. Mi paráfrasis es UI copy generada por agente, sujeta a Middle-Dot Separator Rule. **Test antes de commit**: si el string en `literalContent.ts` puede reescribirse sin alterar significado, es paráfrasis del agente, los em dashes deben ir a `:` / `;` / `(...)`. Si el string es entrecomillado verbatim del source, los em dashes pueden sobrevivir. Caza con `git diff src/.../literalContent.ts | grep -E '^\+' | grep -E '—'` antes de hacer commit.
- **Sub-sistema diatónico como segundo anillo de cuarentena.** El Bloque E introduce `--diatonic-stable`/`--diatonic-medium`/`--diatonic-tense` como tokens de rol diatónico. La tentación para un agente futuro será usarlos decorativamente (ej: "este botón debería verse verde porque es estable"). Regla: los tokens diatónicos son tan semánticos como los `--note-X` — solo pueden usarse en componentes que representen explícitamente un grado dentro de una tonalidad activa (`EscalaMayor`, `TensionResolucion`, y futuros componentes tonales declarados). Test: ¿este elemento es un nodo de `EscalaMayor` o `TensionResolucion`? Sí → token válido. No → usar neutros + `--red`/`--amber`. `GradosArmonicos` usa discriminación tipográfica, no tokens diatónicos — ese es el precedente correcto para componentes donde el color añade ruido, no señal.

- **Un principio transversal de sonido se ancla en el componente compartido, no en N call-sites — y los contextos que NO aplican se documentan como inventario.** El principio "tónica = piso" tenía dos clases de violación: (a) `playNote(note, 4)` fijo en notas sueltas, (b) fórmulas de octava que no manejan el wrap cromático. Para (a), la fix de raíz NO fue tocar ~10 componentes: fue `octaveAboveTonic()` (helper puro) + un solo cambio en `NoteToken` (el componente compartido que renderiza toda nota en prosa/tablas). Extiende los lessons "kill switch en el dispatcher" y "transposición global en el dispatcher": cuando el default correcto depende de estado global (tónica), vive donde la nota se renderiza/reproduce de forma genérica, con prop de escape (`octave`) para los consumidores que ya calculan ascendencias. Para (b), el smell es **cualquier fórmula de octava que no sea `floor((tonicIdx + pos) / 12)`** — `octaveAdj: pos === 12 ? 1 : 0` en TensionResolucion era el mismo bug que la 17ª ola cazó en `closeOctave`, en otro componente. Grep de auditoría: `playNote\(.*,\s*[0-9]` y `octaveAdj|octave: 4` y verificar cada hit contra el inventario de DESIGN.md §7 ("Contextos de sonido"). Tercer punto: la mitad del trabajo fue **decidir y escribir dónde el piso NO aplica** (círculo cromático, rueda de quintas, relativas — identidades absolutas; regla de la 5ª y tríadas — anclados a su raíz local). Sin ese inventario escrito, la próxima auditoría "corrige" las octavas absolutas hacia la tónica y rompe la presentación neutral del círculo.

- **Un guard de fallback texto-plano hereda el formato gráfico de su sibling tokenizado, no el ASCII crudo del dato fuente.** `TablaMaestraSection` cae a `<span>{spelling}</span>` para grafías fuera de las 17 que `NoteToken` soporta (`Cb`, `Fb`, `E#`, `B#`). El bug: el helper `toFlat()` solo convertía `b`→`♭`, dejando `E#`/`B#` en ASCII crudo mientras los chips `NoteToken` adyacentes en la misma fila muestran `♯` unicode — inconsistencia visual silenciosa (no rompe nada, solo se ve "mal tipografiado" al lado de notas bien formateadas). **Test:** cualquier fallback a texto plano junto a un componente que renderiza con glifos especiales debe aplicar el mismo formateo de glifos, no solo manejar el primer caso que el autor tuvo en mente al escribir el regex. Renombrar la función a algo que no sugiera "solo bemoles" (`toFlat` → `toGlyph`) ayuda a que el siguiente accidental no se quede afuera por accidente de nombre.
- **Auditoría "¿está usando NoteToken?" necesita clasificar antes de generalizar — no toda celda de nota es tokenizable.** Al auditar las 7+ tablas de T1/T2 buscando notas en texto plano, la tentación es envolver cualquier match en `<NoteToken>`. Pero el primer criterio de descarte es semántico, no sintáctico: (a) ¿esta tabla oculta alteraciones a propósito por etapa pedagógica? (`IntervalosSection` tabla 1: solo letras naturales, tokenizar reproduciría la nota equivocada); (b) ¿la grafía cae fuera del set canónico de 17 que `NoteSpelling` cubre? (`Cb`/`Fb`/`E#`/`B#` en tonalidades de 6-7 alteraciones); (c) ¿la celda es en realidad un rol/calidad (número romano, "mayor"/"menor") y no una nota individual? Solo después de descartar estos tres casos vale tokenizar. Documentado como Named Rule en DESIGN.md §5 "NoteToken en Tablas".

- **Un hit-area circle SVG sin `pointer-events: all` explícito pierde el hover al disco visible pintado encima, y eso dispara un segundo mouseenter al salir.** `EscalaMayor` tenía un círculo invisible grande (`r=radius+6`) con `onMouseEnter` para detectar hover en todo el nodo, pero el círculo visible (`r=radius`, pintado después en el orden del documento SVG) no tenía `pointer-events: none` — por defecto intercepta el puntero en su propia área. Resultado: el mouse entra al anillo exterior (dispara mouseenter ✓), pero al avanzar hacia el centro el hit-test cambia de elemento (el disco visible, sin handler), y al salir el mouse vuelve a cruzar el anillo, re-disparando mouseenter por segunda vez — sonando la nota dos veces por cada hover real. `ChromaticNode` y `TriadNode` ya tenían el patrón correcto: `.node > * { pointer-events: none }` + `.hit { pointer-events: all !important }`, dejando un único receptor de eventos por nodo. **Test de detección que NO sirve:** `element.dispatchEvent(new MouseEvent(...))` dispara directo en el nodo elegido, sin pasar por el hit-testing real del navegador — no revela este bug. **Test que sí sirve:** `document.elementFromPoint(x, y)` en el centro geométrico del nodo debe resolver al hit-circle, no al círculo visible. Cualquier `<g>` SVG nuevo con hit-area + contenido visual superpuesto debe replicar el patrón `.node > * { pointer-events: none } / .hit { pointer-events: all !important }` desde el primer commit, no como fix posterior.

- **Bebas Neue es all-caps: enmascara cualquier discriminación por minúsculas.** El árbol-constructor (§1.7, 20ª ola) etiquetaba los nodos con su rol interválico (`3m`, `3M`, `5d`, `5`) en Bebas Neue, la fuente display del proyecto. Bebas no tiene glifos de minúscula, así que `3m` y `3M` renderizan **idénticos** (ambos "3M"), y `5d` se ve "5D". El bug es invisible en una lectura del código (el `def.role` string es correcto: "3m") y sólo aparece en el render. Regla: **cualquier texto donde el caso (mayús/minús) porte significado NO puede ir en Bebas Neue.** Bebas se reserva para glifos que ya son mayúscula por naturaleza (letras de nota C/D/E…, headings display). Para roles/calidades/etiquetas donde `m`≠`M` o `dim`≠`Dim`, usar Plex Mono (preserva caso) — mismo eje tipográfico que ya discrimina calidades de acorde en `GradosArmonicos` (10ª ola). Test de detección: si un `<text>`/label en Bebas contiene una letra que debería verse minúscula, está roto; buscar `fontFamily.*Bebas` cerca de strings con minúsculas semánticas. **Corolario (feedback del profesor, 20ª ola):** preservar el caso en monoespaciado NO basta — `m` vs `M` a 14px es demasiado sutil de un vistazo (proyección en clase). Cuando la distinción mayor/menor es pedagógicamente central, redundar la señal: posición (menor a la izquierda, mayor a la derecha) + carril tipográfico (mayor bold recto, menor regular itálica). El caso del glifo es la señal más débil de las tres; nunca la única.
- **Un nodo que ES una nota puede colorearse; su etiqueta de ROL no.** En el árbol-constructor cada nodo representa una nota concreta (la 3m de C es E♭), así que pintar el círculo con `NOTE_COLORS[chromatic]` en hover/selección es uso canónico de la cuarentena (igual que `<NoteToken>`). Pero el **texto de rol** ("3m", "5d") es un nombre de función interválica, no una nota — va en neutro (`var(--text-body)`). La resolución limpia: en reposo el nodo muestra el rol (neutro, Plex Mono); al activarse muestra el **glifo de la nota** (Bebas, blanco sobre el círculo saturado = excepción Signature). Así el color y el glifo-nota aparecen juntos y el rol-neutro nunca se superpone a un fondo saturado. Patrón generalizable a cualquier nodo que tenga doble identidad "función ↔ nota concreta".

- **Verificar hover/focus de React vía automación: dispatchear el evento del que React *sintetiza*, no el sintético.** Al probar el `onMouseEnter`/`onFocus` de un nodo SVG con `preview_eval`, `dispatchEvent(new MouseEvent('mouseenter'))` y `element.focus()` **no** disparan los handlers de React: React no escucha `mouseenter` (lo deriva de `mouseover`/`mouseout` comparando `relatedTarget`) y su `onFocus` viene de `focusin` delegado en root. `.focus()` mueve `document.activeElement` pero no flipea el estado. Lo que sí funciona: `dispatchEvent(new MouseEvent('mouseover', {bubbles:true}))` para enter, y `mouseout` para leave. `onClick` sí mapea de `click` directo (por eso los tests de selección del árbol-constructor funcionaron y los de hover no). Regla de verificación: para handlers de puntero de React, dispatchear `mouseover`/`mouseout`; para focus, `focusin`/`focusout` con `bubbles:true`. Aplica a cualquier verificación browser de primitivas con audio/color on-hover.

### Patrones de a11y observados en la 2ª ola

- **Audio-on-hover sin focus equivalente es la trampa de teclado canónica.** `ChromaticNode`, `TriadNode`, `MasterTriad.chainNote` reproducían audio en `onMouseEnter` solamente. Usuarios de teclado tab-eando recibían cero feedback auditivo. Patrón: cada `onMouseEnter` que dispara un side-effect sensorial (audio, video preview, expanded info) **necesita un `onFocus` paralelo**. Checklist item para cualquier nueva primitive interactiva.
- **SVG `<g>` interactivo es invisible para AT sin role explícito.** Los grupos SVG no tienen role implícito. El patrón `<g onClick={...}>` es un "screen-reader dead zone". Siempre añadir `role="button"` + `tabIndex={0}` + `aria-label` + `onKeyDown` juntos — son un set de cuatro piezas, sacar una rompe el resto.
- **Animar layout properties (`left`, `top`, `width`) es perf tax Y se ignora con `prefers-reduced-motion`** cuando el override CSS global es `* { transition-duration: 0.01ms !important; }`. Switching a `transform` lo hace más rápido (compositor-only) Y mantiene la animación barata de neutralizar. Auditar cualquier `transition: <layout-prop>` mientras se hace una pasada de a11y.
- **`prefers-reduced-motion` requiere counterpart en JS para cualquier animación state-driven.** Las animaciones CSS-only quedan capturadas por el override global del media query, pero las máquinas de estado driven por `setTimeout` / `requestAnimationFrame` / `IntersectionObserver` necesitan checar `matchMedia('(prefers-reduced-motion: reduce)')` ellas mismas y cortocircuitar al estado final. Mismo aplica a manipulación imperativa del DOM.
- **`role="alert"` es el patrón WCAG-AA-compliant para errores transient en formularios** — implica `aria-live="assertive"` y `aria-atomic="true"`, no hay que escribirlos. Para errores de login, submit, otros feedback crítico inmediato. **No usar para status no-crítico** (usar `role="status"` / `aria-live="polite"`).

### Anti-checklist antes de commit

Pasar cada surface por estas preguntas antes de aprobar el cambio:

1. **Cuarentena.** ¿Algún `var(--note-*)`, `var(--string*)`, `var(--caged-*)`, o hex de la paleta cromática está en un componente que **no** representa una nota o acorde? Si sí, violación.
2. **Pure black/white.** `grep` por `#000`, `#fff`, `rgba(0,0,0`, `rgba(255,255,255` en el diff. Cada hit que no sea (a) la letra blanca del Signature Component, (b) la sombra física sancionada del fretboard dot (`rgba(0,0,0,0.6)`), o (c) el hover glow sancionado de Triads (`rgba(255,255,255,0.2)`) — es violación o requiere migración a `var(--paper)`.
3. **Editorial Trio.** ¿Bebas en lowercase? ¿Plex Mono en heading display? ¿Playfair en algo que no sea cita literal de Josué? Cualquier sí → violación.
4. **One H1.** ¿El módulo o vista nueva tiene `<h1>`? Si sí, ¿AppShell ya tiene uno en la misma página? Solo el global tiene `<h1>`.
5. **Module shell.** ¿Renderizás un `<header>` con título dentro de un módulo? Justificá por qué AppShell + Header global no bastan. Default = no.
6. **Em dash / en dash.** `grep "— "` y `grep "– "` en el diff, **incluyendo `.json` y `.md`**. Solo permitido en `Header.tsx` (cita Josué) y archivos `data/literalContent.ts` (contenido del método).
7. **Side-stripe.** `grep "border-left.*[2-9]px\|border-right.*[2-9]px"` en el diff. Cualquier hit fuera de `RuleNote` (legacy reconocido) es violación inmediata. Al eliminar un stripe, revisá `border-radius` y `padding` adyacentes.
8. **Theme-flip.** ¿El componente nuevo lee colores via `var()` para todo lo no-paleta-cromática? ¿Vars referenciadas existen en `:root` Y en `[data-theme="light"]`?
9. **`prefers-reduced-motion`.** ¿El componente nuevo tiene `transition`/`animation`/`@keyframes`? El override CSS global ya neutraliza la duración. Si tu componente tiene una máquina de estado JS (`setTimeout`, `requestAnimationFrame`), añadí check explícito vía `matchMedia('(prefers-reduced-motion: reduce)')`.
10. **Layout property animation.** ¿Animás `width`/`height`/`top`/`left`? Reescribir como `transform`. Sidebar drawer ya lo arregló; no añadir más.
11. **Keyboard reach.** Todo `onClick`/`onMouseEnter` en SVG `<g>`/`<div>` necesita `tabIndex`/`role="button"`/`aria-label`/`onKeyDown` (Enter|Space) **y** `onFocus` si dispara audio/sensory side-effect.
12. **Audio replicado.** ¿Hay feedback solo sonoro en alguna interacción? PRODUCT.md exige paralelo visual: highlight de la nota que suena, posición, color. Audio nunca es el único portador.
13. **Hex repetido.** ¿Estás escribiendo el mismo hex literal por 3ª vez? Pará. Creá un token. Patrón: `:root { X }` + `[data-theme="light"] { Y }` en cualquier archivo de componente es señal directa de que un token global pertenece a `global.css`.
14. **Inline `style` o `React.CSSProperties`.** ¿Estás añadiendo estilos inline? Default a CSS module. Solo reservá inline para valores computados en render que no se pueden expresar como clase + modifier.

### Decisiones doctrinales tomadas (referencia para futuras decisiones similares)

- **N variantes visuales no-nota** se discriminan por: `var(--paper)` para foreground, `var(--muted)` para soporte, `var(--surface-2)` para fondo, `var(--rule)` para divisores, `var(--red)` solo para "tonic role" cuando aplica conceptualmente, `var(--amber)` para CTA primario / activo. Tipografía (Bebas vs Plex), peso (400 vs 500 vs 600), uppercase vs lowercase, letter-spacing — todos válidos como discriminadores antes que el color.
- **`userPicked` state** = `var(--surface-2)` fill + `var(--paper)` stroke. Se distingue de `tonica` (rojo), `highlighted` (ámbar) y `natural` (paper-tint) por contraste tonal, no por hue.
- **Active state pattern** (resuelto en 2ª ola): bg tint del color de marca correspondiente (ej: `rgba(192, 57, 43, 0.08)` para red) + `color: var(--paper)` + `font-weight: 500-600`. Reforzado con chevron (`▾`/`▸`) cuando aplica. **Sin border-left**.
- **Callout banner pattern** (FExceptionBanner): full `border: 1px solid var(--amber)` + `background: rgba(212, 160, 23, 0.06)`. Padding 16-20px. Lee como nota auto-contenida, no como side-stripe alert.
- **`<text>` SVG con `fill="var(--paper)"` o `fill="var(--red)"` funciona** en Vite + browsers evergreen. La lore de "SVG attributes solo aceptan literal colors" está desactualizada.
- **`color-mix(in srgb, var(--token) X%, transparent)`** es el patrón correcto para tints translúcidos basados en CSS vars. Soporte: Baseline 2024 — todos los browsers evergreen modernos. Resuelve el problema de `rgba(var(--paper), X)` que NO funciona (CSS vars no componen dentro de `rgba()` sin un companion `--paper-rgb` token).
- **`prefers-reduced-motion`** se implementa en dos lugares: (a) global CSS en `global.css` con un media query `*` reset que neutraliza duraciones, (b) JS-side en hooks/componentes con `setTimeout`/`requestAnimationFrame` que deben checkar `matchMedia` y saltar a estado final. La pareja CSS+JS es necesaria.
- **Token de texto de cuerpo** (`--text-body`): es un par de luminancia distinto de `--muted`. Texto de párrafo es más legible que labels secundarios; ambos tienen su propio token. Si una pasada futura colapsa `--text-body` en `--muted`, está degradando legibilidad.
- **Em dash → `·` separator** está codificado en DESIGN.md §3 como Middle-Dot Separator Rule. Las JSON i18n (`es.json`/`de.json`) son zona de leak — auditarlas explícitamente.
- **Contenido pedagógico literal va en `data/literalContent.ts` por módulo, nunca en el `.tsx` de la sección ni en `i18n/locales/*.json`.** Doble razón: (a) las erratas y redacción idiomática del método de Josué son **contenido**, no UI copy — separar el qué del cómo; (b) `literalContent.ts` es la única zona donde em/en dashes sancionados pueden aparecer (citas literales del método). Si la prosa vive inline en `.tsx`, los dashes que el método usa contaminan los greps de violación. Patrón: cualquier párrafo que un agente futuro debería **reproducir verbatim** vive como `export const X = "..."` en `literalContent.ts`; el `.tsx` solo orquesta layout + tipografía.

## Procedimiento operativo

Cuando llegue una nueva pasada de craft/polish/distill/harden:

1. Cargar PRODUCT.md y DESIGN.md (el sidecar `.impeccable/design.json` también).
2. Cargar este `lessons-learned.md` antes de empezar.
3. Si la pasada toca color decorativo → ejecutar la **anti-checklist 1, 2, 13**.
4. Si la pasada toca tipografía/copy → **3, 4, 6**.
5. Si la pasada toca layout/animación → **9, 10**.
6. Si la pasada toca interactividad → **11, 12**.
7. Si la pasada introduce estilos → **14**.
8. Al finalizar: actualizar **DESIGN.md §7 Pending Debts** removiendo lo resuelto y añadiendo lo nuevo descubierto. Actualizar este archivo si el patrón de error es nuevo.
